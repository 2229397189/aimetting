# 模块实现质量评价规范（PM Review Rubric）

| 项 | 内容 |
| --- | --- |
| 适用对象 | 本项目所有功能模块（M1 骨架 → M8 工程化）的交付评价 |
| 评价人 | 许清楚（产品经理 / PM） |
| 被评价人 | 寇豆码（software-engineer）；架构问题同步 software-architect |
| 触发时机 | **每完成一个功能模块**，由 team-lead 转交交付内容后立即评价 |
| 评价风格 | **犀利、具体、不吹捧**。该夸夸、该喷喷；优点说清"好在哪、为什么值得保留"，缺点必须定位到 `文件:行号` 并给出可执行改法 |
| 输出去向 | `SendMessage → team-lead`（主）；涉及具体改动的**同时抄送 software-engineer** |

---

## 1. 评价流程（PM 必走 5 步）

| 步 | 动作 | 要求 |
| --- | --- | --- |
| 1 | **读 PRD + 架构文档** | 列出该模块的 P0 功能点与验收标准，形成检查清单 |
| 2 | **读代码** | 按包结构逐层读：Controller → Application/Domain → Service/DAO → 配置。重点看分层是否越界 |
| 3 | **跑测试 / 看测试报告** | **必须实际执行**（Maven/Node），不接受"我写过了"；确认断言是否校验业务内容 |
| 4 | **对照打分** | 按 §2 五维评分表打分，每条扣分必须附证据（文件:行号 或 测试输出） |
| 5 | **出评价 + 回传** | 按 §4 模板输出，SendMessage 给 team-lead，抄送 software-engineer |

> **PM 有权**要求工程师补充信息（如"这个 catch 为什么吞异常"），工程师须在下一轮回应。
> **PM 无权**直接改代码——评价只给结论与建议，修复由工程师执行。

---

## 2. 五维评分标准（每维 1-5 分）

### 维度 1：需求符合度（权重 **30%**）

> 是否完整、准确地实现了 PRD 中该模块的**所有 P0 功能点与验收标准**。

| 分 | 标准 |
| --- | --- |
| **5** | 该模块全部 P0 功能点 100% 实现，且每条**验收标准逐条满足**（含边界场景）；P1 有合理取舍并已记录 |
| **4** | ≥90% P0 实现，个别**非关键**验收点缺失或存在轻微偏差，已主动记录未做项与原因 |
| **3** | 70~90% P0 实现；缺 1~2 个 P0 功能点，或关键验收点有偏差但主流程仍可跑通 |
| **2** | 50~70% P0 实现；主流程勉强可跑但多个 P0 未达标，或"看起来做了"实际与 PRD 描述不符 |
| **1** | <50% 实现，或**核心 P0 未实现**（如 M1 未做 JWT 鉴权） |

**扣分要点**：验收标准中的**可量化指标**（如"BCrypt strength=10"、"连续失败 5 次锁 5 分钟"、"答案 10-5000 字符"）必须与 PRD **逐字对齐**，实现成 6 次/8 位等即扣分。

---

### 维度 2：架构一致性（权重 **20%**）

> 是否严格遵守架构文档的包结构、类签名、分层职责。

| 分 | 标准 |
| --- | --- |
| **5** | 包结构/类签名/命名与架构文档**完全一致**；Controller 零业务逻辑；domain 层**无 Spring 依赖**；接口抽象（CacheService / LockService / SingleFlight / AiProvider）按约定落地且有实现 |
| **4** | 基本一致，存在 1~2 处轻微越界（如 Controller 里一句简单参数判断），不影响扩展与测试 |
| **3** | 存在分层越界：Service 直接拼 SQL / domain 引了 Spring 注解 / 类命名与架构文档不一致；或本应抽象的中间件被硬编码 |
| **2** | 明显违反分层（Controller 写业务编排 / domain 依赖 Spring Bean / 直接 new 依赖），需局部重构 |
| **1** | 完全无视架构文档，自成一派 |

**重点检查项**（对照 `D:\agent-class\aimeeting` 已确认的借鉴点）：
- ✅ 统一返回体 `Result{code:"0", message, data, requestId}` + `Results` 构造器 + `PageInfo`
- ✅ 三级异常 `ClientException / ServiceException / RemoteException` ← `AbstractException(IErrorCode)`，`@RestControllerAdvice` 全局兜底
- ✅ **`@CurrentUser` 方法参数解析器注入登录态，禁用 ThreadLocal**
- ✅ DDD 分包：每域 `api / application / domain / dao / service`
- ✅ 零中间件：缓存/锁/Single-flight 走接口抽象 + Caffeine 实现，**不得出现 Redis 依赖**

---

### 维度 3：代码质量（权重 **20%**）

> 命名、注释、异常处理、硬编码/魔法值、重复代码。

| 分 | 标准 |
| --- | --- |
| **5** | 命名语义化；**无魔法值**（全部常量/配置化）；异常统一走三级体系；重复代码 ≤2 处且已抽象；关键方法注释说明 **why**（而非复述 what）；`AI 调用/状态机/幂等`等核心逻辑注释完整 |
| **4** | 整体良好；≤3 处魔法值或轻微重复；注释基本够用；异常体系使用规范 |
| **3** | 魔法值散落（如直接写 `"0"`、`"ASKING"`、数字 `2` 当追问上限）；重复代码 3~5 处；部分异常被吞（空 catch / 只 `printStackTrace`） |
| **2** | 大量硬编码与字符串判断业务逻辑；异常体系形同虚设（满屏 `RuntimeException`）；几乎没有注释 |
| **1** | copy-paste 堆砌，无法维护 |

**一票否决**：出现 `e.printStackTrace()` 或**空 catch 块且未记日志** → 本项 **≤3**，并列为 P0 必修项。

---

### 维度 4：健壮性（权重 **15%**）

> 边界处理、越权校验、参数校验、降级与兜底。

| 分 | 标准 |
| --- | --- |
| **5** | 全部入参 `@Valid` 校验；**越权校验（BR-15：所有资源查询强制拼 `user_id = @CurrentUser`）** 100% 覆盖；状态机非法跳转被拦截；AI 失败有降级路径 + 兜底文案；幂等生效；空值/超长/超界等边界均有处理**且有单测证明** |
| **4** | 主要校验到位，1~2 处边界未覆盖（如未处理超长输入），无安全问题 |
| **3** | 有参数校验但**缺越权校验**，或 AI 失败直接抛异常给前端（无降级） |
| **2** | 缺少参数校验；或 **mock 模式（无 AI Key）下流程走不通**；或降级逻辑形同虚设 |
| **1** | 无任何防御，非法输入直接 500 |

**一票否决**：存在**横向越权**（A 用户能查到 B 用户的会话/报告/简历）→ 本项 **≤2**，且总结论直接**打回**。

---

### 维度 5：可测试性（权重 **15%**）

> 单测覆盖是否合理、是否可独立验证、断言是否校验业务内容。

| 分 | 标准 |
| --- | --- |
| **5** | 核心逻辑有单测且**断言业务内容**（密码非明文、token 解析出 userId、分数落在 0-100、幂等重放后 LLM 调用次数不增）；外部依赖已 mock；**测试不依赖真实 LLM Key**；mock 模式可独立跑通全流程；测试可重复执行、互不干扰 |
| **4** | 主流程有单测，个别分支未覆盖；覆盖率达 PRD 要求（后端 ≥60%，interview/ai 域 ≥70%） |
| **3** | 有测试但**只断言 HTTP 200 / 非空**；或覆盖率 <60%；或测试执行依赖外部环境 |
| **2** | 几乎无测试；或测试依赖真实 LLM Key（不可重复执行、CI 会挂） |
| **1** | 无测试 |

**一票否决（用户明确要求）**：**只断言 HTTP 200、不校验返回内容** → 本项 **≤2**，并列为 P0 必修项。

---

## 3. 总分计算与结论

```
总分 = 需求符合度×0.30 + 架构一致性×0.20 + 代码质量×0.20 + 健壮性×0.15 + 可测试性×0.15
（满分 5.0，保留 1 位小数）
```

| 结论 | 判定条件 | 后续动作 |
| --- | --- | --- |
| ✅ **通过** | 总分 **≥ 4.3** 且 **无 P0 必修项** | 允许进入下一模块；P1/P2 进入 backlog 排期 |
| ⚠️ **有条件通过** | 总分 **3.5 ~ 4.3**，或存在 P0 必修项但范围可控 | **P0 必修项必须在下一模块开工前闭环**；PM 复核通过后放行；P1 可排期 |
| ❌ **打回** | 总分 **< 3.5**，**或** 触发任一**一票否决**（横向越权 / 只断言 200 / 空 catch） | 停止后续模块开发，工程师修复后**重新提交完整模块复审** |

> **打回不是惩罚，是止损**。发现越权或测试造假时越早打回，返工成本越低。PM 需明确写出"修到什么程度可以放行"。

## 5. 评价红线（违反即触发打回或强制 P0）

| # | 红线 | 后果 |
| --- | --- | --- |
| R-1 | **横向越权**：可查询/修改其他用户的数据 | ❌ 打回 |
| R-2 | **测试只断言 HTTP 200**，不校验返回内容 | 可测试性 ≤2 + P0 必修 |
| R-3 | **空 catch / `printStackTrace()` 且未记日志** | 代码质量 ≤3 + P0 必修 |
| R-4 | **AI 失败直接抛异常给前端**，无降级无兜底文案 | 健壮性 ≤3 + P0 必修 |
| R-5 | **无 AI Key 时主流程跑不通**（违反 PRD G4） | ❌ 打回（这是硬需求） |
| R-6 | 引入 **Redis / MongoDB 等不可用中间件作为强依赖** | 架构一致性 ≤2 + P0 必修 |
| R-7 | 使用 **ThreadLocal 传递登录态**（应为 `@CurrentUser`） | 架构一致性 ≤3 + P0 必修 |
| R-8 | 密码/密钥 **硬编码或明文落库** | ❌ 打回 |
| R-9 | **Controller 内写业务编排逻辑**（分层越界） | 架构一致性 ≤3 + P1 必修 |
| **R-10** | **修改 prompt 模板未递增 `prompt_version`**（Δ1-4 面试官质量评估体系） | 代码质量 ≤4 且记 P1 缺陷 |

> **R-10 说明**：`prompt_version` 是「可评测的面试官」护城河的追溯基石（见 `PRD-DELTA-1.md` §11）。版本漂移会让 golden set 一致性报告失去可比性。PM 评价 M3/M4/M8 时**必查**：`PromptVersions` 常量值、模板文件名版本、落库值三者是否一致。

## 7. 沟通约定

| 场景 | PM 动作 |
| --- | --- |
| 评价通过 | SendMessage → team-lead（结论+要点）；无需抄送工程师 |
| 有条件通过 / 打回 | SendMessage → team-lead（完整评价）**+ 抄送 software-engineer**（列出 P0 必修项，便于直接开工修） |
| 发现架构级问题（与架构文档冲突） | SendMessage → software-architect（抄送 team-lead） |
| 需要工程师补充信息 | SendMessage → software-engineer（明确问什么、为什么要） |

**禁止**：`整体不错，建议继续优化` 这类无信息量的评价。每一条优点和缺点都必须能被读者**直接定位到代码**。
