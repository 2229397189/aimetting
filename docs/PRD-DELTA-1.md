## 0. 变更背景

### 0.1 调研的决定性发现

> **全行业（开源 + 商业）没有一家公开做"面试官质量评估体系"**——评测集、评分一致性指标、prompt 版本化对比均为空白。开源项目（`llx9826/llm-interview-coach`）甚至被评测文章直接点名批评"无评估指标"。

这说明：**差异化护城河不在"能出题"，而在"面试官可评测"**。本项目的 A 脊柱（可评测的面试官）选择得到印证。

### 0.2 识别到的自身差距（aimeeting vs 竞品）

| 差距 | 竞品做法 | 补齐成本 | 决策 |
| --- | --- | --- | --- |
| **只有简历、没有 JD** | 面灵AI、Interviewer_AI 均支持简历+JD 双输入定制出题 | 1 个输入框 + prompt 上下文 | **v1 吸收（Δ1-1）** |
| **单阶段平铺出题** | Interviewer-AI-Agent 阶段化编排（Warmup→技术→系统设计→收尾） | 状态机天然支持，加一个 `currentStage` 字段 | **v1 吸收（Δ1-2）** |
| **报告无"改进后的参考答案"** | Interviewer-AI-Agent 每题附改进答案重写 | 1 次批量 prompt + 1 个字段 | **v1 吸收（Δ1-3）** |

### 0.3 顺带吸收的工程纪律（不新增功能点，但必须遵守）

| # | 纪律 | 来源 | 落地方式 |
| --- | --- | --- | --- |
| D-1 | **出题 prompt 与评分 prompt 严格分离** | TakPrince | 两套 prompt 模板独立文件，禁止共用变量；出题 prompt 中禁止出现评分维度描述，评分 prompt 中禁止出现出题指令 |
| D-2 | **JSON 结构化输出 + 容错解析** | Interviewer-AI-Agent | AI 输出统一要求 JSON；解析失败→重试 1 次→降级规则，禁止直接把原始文本当结果 |
| D-3 | **问题 hash 去重** | Interviewer-AI-Agent | 题干 MD5 存入会话级去重集合（Caffeine Set），出题与追问均校验（原 BR-17 已覆盖，此处扩展到追问） |

## 1. Δ1-1 简历 + JD 双输入定制出题

### 1.1 用户故事

| ID | 用户故事 |
| --- | --- |
| US-D1-1 | 作为**在校生**，我希望在开一场面试前可以粘贴目标岗位的 JD，这样 AI 出的题能对准这家公司的真实要求，而不是泛泛而问 |
| US-D1-2 | 作为**应届求职者**，我希望系统能告诉我"JD 要求但简历里没有的技能"，这样我知道该补什么、该在简历里怎么包装 |
| US-D1-3 | 作为**转岗者**，我希望 JD 不填也能正常面试，这样没有明确目标岗位时也能练手 |
| US-D1-4 | 作为**用户**，我希望保存过常用 JD 后能直接复用，这样投多家公司时不用反复粘贴 | ⏸ **暂缓** |

> ⏸ **US-D1-4 暂缓说明**（team-lead 拍板 Q-D1-1）：v1 **不新建** `t_job_description` 表，JD 仅以 `jd_snapshot` 冗余落会话表。因此"保存/复用 JD"能力无存储载体，**延后实现**，US-D1-1~3 不受影响。

### 1.2 需求定义

#### 1.2.1 JD 录入入口

| 入口 | 优先级 | 形态 | 说明 |
| --- | --- | --- | --- |
| **A. 面试配置页 `/interview/setup`**（主入口） | **P0** | Element Plus `el-textarea` 折叠面板，标题「目标岗位 JD（选填）」，placeholder 提示"粘贴 JD 可让题目更贴合目标岗位" | 与「简历绑定」并列，二者皆可选 |
| B. JD 管理页（`/jd`，与 `/resume` 并列 tab） | ⏸ **暂缓**（原 P1） | 列表 + 新增/编辑/删除 + 「使用此 JD 开一场面试」跳转 | **v1 不实现**（依赖 `t_job_description` 表，已拍板不建表）。API #56/57/58 同步暂缓 |
| C. 会话内补填 | P2 | 会话详情页允许 INIT 状态下补填 JD | 非 INIT 状态禁止修改（快照一致性） |

#### 1.2.2 JD 字数与合法性

| 规则 | 定义 |
| --- | --- |
| 长度上限 | **3000 字**（trim 后计，中文 1 字 = 1 字符）。超过：**前端 `maxlength` 截断 + 后端兜底截断至 3000**，返回 `degraded` 轻提示"JD 已超出 3000 字，超出部分不参与出题" |
| 有效下限 | **20 字**。< 20 字（或纯空白/纯符号）视为**无效 JD**：不报错、不阻断，按 `jdText == null` 同等处理，返回提示"JD 过短，将仅依据简历与方向出题"，`hasJd=false` |
| 允许为空 | 是。`jdText` 为 null/blank 时：**出题 prompt 不注入 JD 段落**，不额外调用 LLM 做 JD 生成或补全 |
| 存储 | 会话表冗余快照 `jd_snapshot`（TEXT），**题库/报告均读快照**，保证历史可回溯、JD 原文后续修改不影响已完成的面试 |
| 注入 prompt 上限 | **JD 裁剪至 ≤1500 字 + 简历摘要 ≤800 字** 注入出题 prompt（性能与 token 成本控制，见 §5 风险 R1） |

#### 1.2.3 简历与 JD 冲突时的优先级（关键规则）

**原则：JD 是"考察目标"，简历是"素材来源"。**

| 优先级 | 选题依据 | 目标占比 | 标记 |
| --- | --- | --- | --- |
| 1 | **JD ∩ 简历**（JD 要求的技能，简历中也确实有） | ≥ **40%** 题量 | 无 |
| 2 | **JD 独有**（JD 要求但简历未体现） | 次之 | `jdGap = true` |
| 3 | **简历独有**（简历有但 JD 未提） | 再次 | 无 |
| 4 | **通用题库**（按方向+难度兜底） | 兜底 | `source = BANK` |

**冲突处理规则（BR-D1-01）**：
1. JD 要求某技术栈 X 而简历无 X → **仍出题**，题干前缀标注「岗位要求项」，打标 `jdGap=true`；
2. 报告汇总所有 `jdGap=true` 题目的技能点，输出 **「JD 技能缺口清单」**（见 Δ1-2 报告变更）；
3. 简历与 JD 方向严重不匹配（如 JD 前端 / 简历 Java）→ **不阻断、不报错**，按上述优先级正常出题（匹配度评分列 P1，见 Q-D1-9）；
4. **禁止**因 JD 与简历不匹配而拒绝创建会话或抛异常。

#### 1.2.4 验收标准

| # | 验收标准 |
| --- | --- |
| AC-D1-1-1 | 创建会话时传 `jdText`（≥20 字）成功落库，详情接口可原样返回；`hasJd=true` |
| AC-D1-1-2 | `jdText` 为空 / <20 字：`hasJd=false`，会话可正常创建并完成整场面试，出题不报错 |
| AC-D1-1-3 | `jdText` > 3000 字：后端截断至 3000，返回提示，会话正常创建 |
| AC-D1-1-4 | 传 JD 时，出题 prompt 中**必须同时出现** JD 关键技能词与简历项目关键词（单测断言 prompt 构建结果包含二者） |
| AC-D1-1-5 | 仅传 JD 不传简历：可正常出题（JD 独有 + 通用兜底），不报错 |
| AC-D1-1-6 | 仅传简历不传 JD：行为与 Δ1 之前完全一致（**回归要求**） |
| AC-D1-1-7 | JD 与简历方向完全相反（JD 前端 / 简历 Java 后端）：可完成整场面试，`jdGap` 题被正确标记 |
| AC-D1-1-8 | Mock 模式（无 Key）下传 JD：仍能出题且不抛异常，题目来自预置题库按方向+阶段抽取 |
| AC-D1-1-9 | 注入 prompt 的 JD ≤1500 字、简历摘要 ≤800 字（单测断言长度上限） |

## 2. Δ1-2 三阶段面试流程（技术面 → 项目面 → 行为面）

### 2.1 用户故事

| ID | 用户故事 |
| --- | --- |
| US-D1-5 | 作为**应届求职者**，我希望一场面试按"技术→项目→行为"推进，这样节奏像真实面试，而不是随机题目堆砌 |
| US-D1-6 | 作为**在校生**，我希望界面上能清楚看到"现在在第几阶段、这一阶段还剩几题"，这样心里有底 |
| US-D1-7 | 作为**转岗者**，我希望行为面的反馈能明确告诉我 STAR 里哪一环（S/T/A/R）讲得最差，这样我知道该怎么改叙述结构 |
| US-D1-8 | 作为**用户**，我不希望技术面也被套用 STAR 评价，那样反馈会不伦不类 |

### 2.2 阶段定义

| 阶段 Enum | 中文名 | 默认占比 | 考察重点 | STAR 反馈 |
| --- | --- | --- | --- | --- |
| `TECHNICAL` | 技术面 | **50%** | 语言/框架/中间件/数据库/网络/OS/算法等技术知识点 | **不启用** |
| `PROJECT` | 项目面 | **30%** | 简历项目的架构选型、难点、权衡、量化结果、踩坑 | **不启用** |
| `BEHAVIORAL` | 行为面 | **20%** | 团队协作、冲突处理、抗压、成长性、职业规划 | **启用** |

顺序单向不可逆：`TECHNICAL → PROJECT → BEHAVIORAL → 结束`。暂停/恢复**保留**当前阶段与阶段内进度。

### 2.3 题量分配与取整规则（关键算法，BR-D1-02）

```
输入：总题量 N（3 ≤ N ≤ 15），比例 ratio = [50, 30, 20]（可配，三者之和必须 = 100）

步骤 1：raw_i   = N * ratio_i / 100
步骤 2：base_i  = floor(raw_i)
步骤 3：diff    = N - Σ base_i
步骤 4：按 raw_i 的【小数部分】从大到小，依次给 base_i + 1，直到 diff 用完
        小数部分相同时，按固定优先级 TECHNICAL > PROJECT > BEHAVIORAL
步骤 5：兜底（仅在比例被配置成极端值时触发）：
        若某阶段 base_i == 0 且 ratio_i > 0 → 强制 base_i = 1，
        并从【当前分配数最大】的阶段扣 1（并列时按 BEHAVIORAL > PROJECT > TECHNICAL 顺序扣）
步骤 6：校验 Σ base_i == N 且 每个 base_i ≥ 1，否则 fail-fast 抛异常
```

**配置校验**：`interview.stage-ratio=50:30:20`，应用启动时校验三项之和 = 100，否则 **fail-fast 启动失败**（不允许带病启动）。

**取整示例表（开发请照此写单测）**

| N | raw (T/P/B) | 小数部分排序 | 最终分配 (T/P/B) |
| --- | --- | --- | --- |
| 3 | 1.5 / 0.9 / 0.6 | P(.9) > B(.6) > T(.5) | **1 / 1 / 1** |
| 4 | 2.0 / 1.2 / 0.8 | B(.8) | **2 / 1 / 1** |
| 5 | 2.5 / 1.5 / 1.0 | T(.5) = P(.5) → 优先级 T | **3 / 1 / 1** |
| 6 | 3.0 / 1.8 / 1.2 | P(.8) | **3 / 2 / 1** |
| 7 | 3.5 / 2.1 / 1.4 | T(.5) | **4 / 2 / 1** |
| 8（默认） | 4.0 / 2.4 / 1.6 | B(.6) | **4 / 2 / 2** |
| 9 | 4.5 / 2.7 / 1.8 | B(.8) > P(.7) | **4 / 3 / 2** |
| 10 | 5.0 / 3.0 / 2.0 | 无余数 | **5 / 3 / 2** |
| 12 | 6.0 / 3.6 / 2.4 | P(.6) | **6 / 4 / 2** |
| 15 | 7.5 / 4.5 / 3.0 | T(.5) = P(.5) → 优先级 T | **8 / 4 / 3** |

> 默认题量 8 → **技术面 4 题 / 项目面 2 题 / 行为面 2 题**。

### 2.4 阶段切换的用户可见表现

| 位置 | 表现 |
| --- | --- |
| 顶部 `ElSteps` | 3 步横向步骤条：技术面 → 项目面 → 行为面，已完成阶段打勾，当前阶段高亮 |
| 分段进度条 | 3 段独立进度条（宽度按阶段题量比例），当前段内显示「第 x / y 题」 |
| 阶段徽章 | 题干卡片右上角 `StatusBadge`，显示当前阶段中文名 + 配色（技术蓝 / 项目橙 / 行为绿） |
| 切换提示 | 阶段切换时在对话流中插入**系统气泡**：「—— 技术面结束，进入项目面 ——」 |
| 前端过渡 | 切换时有 300ms 淡入动画，不做全屏遮罩（避免打断） |
| 报告页 | 分阶段得分卡片（技术面分 / 项目面分 / 行为面分）+ 各阶段逐题点评分区展示 |

### 2.5 阶段推进逻辑

| 规则 | 定义 |
| --- | --- |
| 阶段内耗尽 | 当前阶段已答题数 == 该阶段分配题数 → 自动进入下一阶段，**无需用户操作** |
| 最后阶段耗尽 | BEHAVIORAL 完成 → 自动 `COMPLETED` 并触发报告生成 |
| 追问不计题量 | **追问（follow-up）不计入阶段题量**，不推进 `questionNo`，仅挂在原题下（维持原 BR-01：每题最多 2 次追问） |
| 跳过题 | 跳过的题**计入**阶段题量并记 0 分，正常推进 |
| 主动结束 | 用户在任意阶段点「结束面试」→ 以**已完成题目**生成报告，未完成的阶段不参与分阶段得分（该阶段分记为 null，前端显示"—"） |
| 状态分离 | **阶段是流程细状态，不污染会话主状态**。会话主状态仍为 `INIT/ASKING/...`（持久化于 `t_interview_session.status`），阶段由 `current_stage` + `stage_question_index` 表达，两者互相独立 |

### 2.6 STAR 结构反馈（仅行为面）

#### 2.6.1 启用范围

| 阶段 | STAR 反馈 | 后端强制校验 |
| --- | --- | --- |
| `BEHAVIORAL` | **启用** | — |
| `TECHNICAL` / `PROJECT` | **不启用** | 若 AI 返回 `starWeakest != NONE`，后端**强制置为 `NONE`** 并打印 warn 日志（防止 prompt 串味），前端不渲染 STAR 卡片 |

#### 2.6.2 输出定义

| 字段 | 类型 | 优先级 | 说明 |
| --- | --- | --- | --- |
| `starWeakest` | Enum `S / T / A / R / NONE` | **P0** | 最薄弱的一环；非行为面强制 `NONE` |
| `starAdvice` | String(≤100 字) | **P0** | 一句话指出该环薄弱的具体改进（例："缺少可量化结果，建议补上'性能提升 40%'这类数字"） |
| `starDetail{S,T,A,R}` | 各 0-100 整数 | P1 | 四环细分分，报告里可出小雷达图 |

- **S** = Situation（背景）、**T** = Task（任务）、**A** = Action（行动）、**R** = Result（结果）
- 值为 `NONE` 的合法场景：非行为面，或行为面答案过于简短无法判定（此时 `starAdvice` 给"答案过短，建议用 STAR 结构重述"）

#### 2.6.3 Mock 模式的 STAR 判定（规则引擎）

按关键词命中缺失判定最弱环（**无需 LLM**）：

| 环 | 命中关键词（任一） |
| --- | --- |
| S | 背景 / 当时 / 情况 / 项目初期 / 团队 |
| T | 任务 / 目标 / 负责 / 需要 / 要求 |
| A | 我做了 / 我负责 / 行动 / 实现 / 方案 / 推动 |
| R | 结果 / 最终 / 提升 / 降低 / 完成 / 数据 / % |

判定：四环均未命中 → `NONE`；仅一环未命中 → 该环为 `starWeakest`；多环未命中 → 按 **R > A > T > S** 的固定顺序取第一个未命中环（结果缺失危害最大）。

#### 2.6.4 验收标准

| # | 验收标准 |
| --- | --- |
| AC-D1-2-1 | 题量 N ∈ [3,15] 时，分配结果与 §2.3 示例表**完全一致**（单测逐行断言） |
| AC-D1-2-2 | Σ 分配题量 == N 且每阶段 ≥1（单测 property 校验 N=3..15 全覆盖） |
| AC-D1-2-3 | 比例配置之和 ≠ 100 时应用**启动失败**（fail-fast） |
| AC-D1-2-4 | 阶段自动推进：技术面最后一题评分完成后，下一题自动为项目面题，且 `currentStage` 字段已更新 |
| AC-D1-2-5 | 追问不推进 `questionNo`、不计入阶段题量（单测：连做 2 次追问后 `stageQuestionIndex` 不变） |
| AC-D1-2-6 | 行为面答案返回 `starWeakest ∈ {S,T,A,R,NONE}` 且 `starAdvice` 非空 |
| AC-D1-2-7 | 技术面/项目面答案返回 `starWeakest == NONE`；**即使 mock AI 故意返回 "A"，后端也强制置为 NONE**（单测覆盖此防御） |
| AC-D1-2-8 | 前端：阶段切换时步骤条、分段进度条、徽章、系统气泡**四者同步更新** |
| AC-D1-2-9 | 中途结束：未完成阶段得分为 null，报告不报错、不显示 0 分 |
| AC-D1-2-10 | 暂停后恢复，阶段与阶段内进度完全保留 |

### 2.7 报告变更（分阶段得分）

| 变更 | 定义 |
| --- | --- |
| `stageScoreJson` | `{"TECHNICAL": 78.5, "PROJECT": 65.0, "BEHAVIORAL": null}`；未完成阶段为 `null`，前端显示"—" |
| **总分计算（修订原 BR-02 后半句）** | 单题得分仍按「原题 70% + 追问均分 30%」；**总分 = Σ(阶段均分 × 阶段占比)**，仅对已完成阶段归一化（例：只完成技术面 → 总分 = 技术面均分） |
| 报告新增区块 | ① 三阶段得分卡片 ② **JD 技能缺口清单**（`jdGap=true` 题目的技能点聚合，无 JD 时该区块隐藏）③ 行为面 STAR 汇总（出现频次最高的薄弱环 + 汇总建议） |

> ⚠️ **BR-02 修订说明**：原「总分 = 各题加权平均」改为「总分 = 分阶段加权」。理由：阶段占比是本次核心设计，总分需与阶段权重一致才具备解释性。单题内部的 70/30 权重规则不变。

## 3. Δ1-3 报告附「改进后的参考答案」

### 3.1 用户故事

| ID | 用户故事 |
| --- | --- |
| US-D1-9 | 作为**在校生**，我希望答得不好的题能看到"标杆答案长什么样"，这样我知道差距在哪、该背什么 |
| US-D1-10 | 作为**应届求职者**，我希望改进答案只出现在低分题上，这样报告不会又长又水 |
| US-D1-11 | 作为**用户**，我希望导出的 Markdown 里也带改进答案，方便我离线复习 |

### 3.2 需求定义

| 项 | 定义 |
| --- | --- |
| **触发阈值** | 单题**最终得分 < 80**（含追问加权后的最终分）。可配 `report.improved-answer-threshold=80` |
| **字数范围** | **150 ~ 400 字**。>400 截断并追加"…"；<150 视为解析失败 → 重试 1 次 → 仍失败则**该题不展示改进答案**（不阻塞报告，标记 `improvedAnswerBy=NONE`） |
| **生成时机** | **P0：报告生成时统一批量生成**（见下方"为什么不在答题流里生成"） |
| **批量策略** | 单次 prompt 最多处理 **5 题**，超过则分批串行调用；报告超时由 120s **放宽至 180s** |
| **部分失败** | 某批失败 → 该批题目 `improvedAnswerBy=NONE`，**报告主体正常产出**，前端该题目不展示折叠面板 |
| **存储** | `t_session_question.improved_answer` + `improved_answer_by`（AI/RULE/NONE）——按题存储，便于会话详情回看时也能看到 |
| **展示位置** | 报告「逐题点评」区块内，该题卡片底部 `ElCollapse` 折叠面板，标题「💡 改进后的参考答案（AI 生成）」，默认**折叠** |
| **Markdown 导出** | **包含**，作为每题下的 `### 改进后的参考答案` 小节（默认展开文本，不折叠） |
| **Mock 模式** | 用该题 `reference_points`（参考答案要点）拼接为 200 字左右模板文本，标记 `RULE`，前端显示"（规则生成）"角标 |

**为什么不在答题流里生成（P0 决策说明）**：
- 答题即时生成会使单题等待时间 +10~20s，直接违反原 PRD 非功能指标「SSE 首 token ≤3s、单题评分 ≤15s」
- 用户答完题最想先看到**分数和点评**，改进答案是"事后复习"需求，属于报告场景
- P1 可选：报告生成后提供「补生成/重新生成」接口，用户在报告页手动触发

### 3.3 验收标准

| # | 验收标准 |
| --- | --- |
| AC-D1-3-1 | 得分 ≥80 的题目：`improvedAnswer == null` 且前端不渲染折叠面板 |
| AC-D1-3-2 | 得分 <80 的题目：`improvedAnswer` 长度 ∈ [150,400]，非空、与题干相关 |
| AC-D1-3-3 | 全部题目 ≥80（无低分题）：**不调用**改进答案生成（单测断言 LLM 调用次数 = 0） |
| AC-D1-3-4 | AI 返回 <150 字：重试 1 次后仍失败 → `improvedAnswerBy=NONE`，报告正常产出（不抛异常） |
| AC-D1-3-5 | 15 题全为低分：分 3 批串行调用，报告在 180s 内产出 |
| AC-D1-3-6 | 报告导出 Markdown 包含所有已生成的改进答案小节 |
| AC-D1-3-7 | Mock 模式下改进答案为规则生成，长度 ≥150 字，标记 `RULE`，全流程不抛异常 |
| AC-D1-3-8 | 会话详情回看（`/interview/{id}`）也能看到改进答案 |
| AC-D1-3-9 | 改进答案生成**不影响**报告总分、五维分、雷达图（回归要求） |

## 8. 风险与缓解

| # | 风险 | 影响 | 缓解措施 |
| --- | --- | --- | --- |

## 11. Δ1-4 面试官质量评估脚手架（**v1 落地**，归 M8 模块）

### 11.1 背景：行业空白，也是我们唯一的护城河

> 调研决定性发现：**全行业（开源 + 商业）没有一家公开做"面试官质量评估体系"**——评测集、评分一致性指标、prompt 版本化对比均为空白。开源项目被评测文章直接点名批评"无评估指标"。

**产品推论**：竞品比的是"能不能出题"，我们比的是"**这个面试官可不可信**"。没有度量就没有可信度；没有可信度，报告再漂亮也只是"感觉挺准"。

**v1 目标**：不建复杂平台，只做 **4 件低成本、可落地**的事，让"面试官质量"第一次变得**可追溯、可测量、可证明**。

**三条铁律**：
1. **不增加线上复杂度**——3 件是观测/统计（读已有日志表），1 件是离线脚本（不进运行时）
2. **不阻塞主流程**——脚手架任一环节失败，不影响任何用户功能（AC-D1-4-12）
3. **可写进简历**——这是陆强面试时唯一能讲出"我和别人不一样"的地方，必须能量化、能演示

### 11.3 四件事

#### 11.3.1 D1-4-1 prompt 版本化（P0）

| 项 | 定义 |
| --- | --- |
| 落库 | `t_ai_call_log` + `prompt_version`(varchar 16)，**每次 AI 调用必写，非空** |
| 版本格式 | `{BIZ_TYPE}-v{n}`：`GENERATE_QUESTION-v1` / `EVALUATE-v1` / `GENERATE_REPORT-v1` / `PARSE_RESUME-v1` / `IMPROVE_ANSWER-v1` |
| 常量管理 | 集中在 `PromptVersions` 常量类（或 enum），**禁止代码里散落版本字符串** |
| 模板文件 | `resources/prompts/evaluate-v1.txt` 等，**文件名带版本**，启动时加载进缓存 |
| **纪律** | **修改 prompt 模板必须递增版本号**——已写入 `REVIEW-RUBRIC.md` 红线 **R-10**（PM 评价必查项） |

#### 11.3.2 D1-4-2 golden set 一致性脚本（P0，离线）

| 项 | 定义 |
| --- | --- |
| 数据集 | `src/test/resources/eval/golden-set.json`：**10 题 × 5 档固定答案 = 50 条样本** |
| 覆盖要求 | 10 题须覆盖 3 阶段（技术/项目/行为）+ 3 难度 + ≥2 方向，每格 ≥1 题 |
| 5 档答案 | 优秀 / 良好 / 中等 / 较差 / 离题——**人工撰写固定文本**，不随 LLM 变化（否则无法做一致性基线） |
| 执行方式 | 每题每档跑 **3 次** = 150 次调用；`mvn.cmd test -Peval` 或 `tools/eval/run-consistency.sh` |
| 输出指标 | ① 同档 3 次的**标准差 σ** ② 同档**极差** ③ **档位单调性**（5 档均分是否单调递减）④ 汇总：全体 σ 均值、最大极差、单调性违规题数 |
| 产出物 | `docs/eval/consistency-report-{yyyyMMdd}.md`：50×3 原始分数表 + 自动 PASS/FAIL 判定 |
| **通过门槛** | 同档 **σ ≤ 8 分**；同档**极差 ≤ 15 分**；单调性 **≥ 4/5** 相邻档递减（允许 1 处持平） |
| CI 策略 | **不进 CI 必过**（需真实 Key、约 10~20 min）。提供 **smoke 模式**（2 题×2 档×2 次 = 8 次调用）用于验证脚本本身可跑 |
| Mock 模式 | 直接 **SKIP** 并输出说明（规则引擎不参与一致性评测，跑了也是满分无意义） |

#### 11.3.3 D1-4-3 评分分布观测（P0）

| 项 | 定义 |
| --- | --- |
| 位置 | `GET /api/admin/ai/health` 增加 `scoreStats` |
| 样本 | 最近 **100 条** `biz_type = EVALUATE` 且 `success = 1` 且 **`degraded = 0`** 的记录 |
| ⚠️ 关键过滤 | **降级评分（规则引擎产出）不计入分布**，否则分布会被兜底分数稀释，失去观测意义 |
| 统计值 | `count / mean / stdDev / min / max / p50 / p95` |
| 直方图 | 五桶：`0-20 / 20-40 / 40-60 / 60-80 / 80-100` |
| 分组对比 | **按 `prompt_version` 分组**输出——换 prompt 后分数整体抬高或压低，一眼可见分布漂移 |
| 数据源 | `t_ai_call_log` + `score`(int, nullable)，评分成功时写入 |
| 前端 | M8 管理端 dashboard 增加「评分分布」卡片（ECharts 柱状图 + 关键统计值） |

#### 11.3.4 D1-4-4 degraded 率指标（P0）

| 项 | 定义 |
| --- | --- |
| 判定 | `degraded = 1` **当且仅当** `ai.provider != mock` 且本次调用因 **失败/超时/熔断/舱壁打满/JSON 解析失败** 而**回退到规则引擎** |
| ⚠️ **关键区分** | **`ai.provider=mock` 是预期执行路径，不是降级**，必须计 `degraded = 0`。否则 mock 模式下该指标恒为 100%，完全失去意义（AC-D1-4-11 强制校验） |
| 统计维度 | 按 `bizType` 分组：`total` / `degraded` / `degradedRate` / `failureRate` / `avgCostMs` / `topErrorTypes[]` |
| 落库 | `t_ai_call_log` + `degraded`(tinyint)，复用已有 `error_type` |
| 接口 | `GET /api/admin/ai/health` 增加 `degradedStats[]` |
| 前端 | M8 dashboard 增加「AI 稳定性」卡片：降级率 + 失败原因 Top3 |

### 11.5 验收标准（AC-D1-4-1 ~ 12）

| # | 验收标准 |
| --- | --- |
| AC-D1-4-1 | 每条 AI 调用日志都带 `prompt_version`，非空且格式 `{BIZ}-v{n}` |
| AC-D1-4-2 | 修改 prompt 模板后版本号递增（单测：`PromptVersions` 常量与模板文件名版本**一致**） |
| AC-D1-4-3 | 版本集中管理——全仓搜索版本字符串，只应出现在 `PromptVersions` 与模板文件名中 |
| AC-D1-4-4 | `golden-set.json` 含 50 条样本，覆盖 3 阶段 + 3 难度 + ≥2 方向 |
| AC-D1-4-5 | 脚本可跑通，报告含 50×3 = 150 条原始分数 |
| AC-D1-4-6 | 报告自动判定 PASS/FAIL（σ≤8、极差≤15、单调性 ≥4/5） |
| AC-D1-4-7 | smoke 模式（8 次调用）可跑通；mock 模式下脚本 **SKIP** 并输出说明 |
| AC-D1-4-8 | 造 100 条评分日志后，`scoreStats` 的 mean/stdDev/p95 与 SQL 聚合结果**完全一致**（单测） |
| AC-D1-4-9 | 五桶直方图计数之和 == count |
| AC-D1-4-10 | 造 10 次降级 + 10 次正常 → `degradedRate = 50%` |
| AC-D1-4-11 | **mock 模式下 `degradedRate = 0`**（防污染，必有单测） |
| AC-D1-4-12 | 脚手架任一环节失败（如日志表查询异常）**不影响** `/api/admin/ai/health` 主体返回，更不影响任何用户功能 |

### 11.6 风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| R7 | golden set 全量跑 ~150 次调用，成本与耗时（10~20 min） | smoke 模式；**不进 CI 必过**；手动触发；报告纳入 git 形成历史对比，无需每次全量跑 |
| R8 | **改了 prompt 忘记递增版本号**（无法自动检测，会毁掉整套追溯能力） | ① 模板文件名强制带版本 ② **`REVIEW-RUBRIC.md` 红线 R-10**：改 prompt 未递增版本 = P1 缺陷，PM 评价必查 ③ PR 检查清单项 |
| R9 | 降级（规则）评分若计入分布，会稀释统计、掩盖真实 AI 表现 | 明确：`scoreStats` **只统计 `degraded = 0`** 的记录；规则评分的分数单独在 `degradedStats` 侧体现 |
